## 1. 🗂️ Database Indexing → [full note](../database-indexing.md)

**The core trade-off:** an index trades slower writes + extra storage for far faster reads. Turns "read everything and filter" (`O(n)`) into "jump straight there" (`O(log n)`).

What actually stuck:

- Most indexes are **B+Trees** — balanced, high fan-out, with **sorted linked leaves**. That leaf chain is what makes range queries and `ORDER BY` cheap.
- **Clustered vs. non-clustered** is the concept I kept underestimating: a secondary-index lookup can cost *two* traversals (the "bookmark lookup"). In InnoDB the PK *is* the clustered index.
- **Covering indexes** kill the second lookup — if the index holds every column the query needs, the table is never touched ("index-only scan"). High leverage.
- **Composite index column order matters** (left-prefix rule): equality columns first, range/sort column last.
- Always confirm with `EXPLAIN` — and remember **selectivity**: an index that doesn't eliminate most rows won't be used.

> One-liner to remember: *an index is a sorted copy of some columns + pointers to rows, kept current on every write.*

## 2. 🔁 Loop Engineering → [full note](../loop-engineering.md)

**The mental shift:** the unit of leverage moved from the **prompt** (typed once) to the **loop** (runs while you sleep). An *agent* is a worker; a *loop* is what makes the worker improve after the first attempt.

What actually stuck:

- The core loop is five verbs: **gather → reason → act → verify → repeat**, wrapped around Memory, State, a Verifier, a Stop condition, and Cost.
- **Separate the roles** — planner, generator, evaluator get different context windows. A model that grades its own work converges on slop.
- **Negotiate the contract first** — agree on testable criteria *before* writing code; the contract is what gets graded.
- **Write to disk, not to context** — context windows rot; state in files survives crashes and restarts.
- **Letting the loop restart is often correct**, not a failure. Intervene when the *contract* is wrong, not when the build is.
- Karpathy's kicker: **the bottleneck always moves** — solve coding, planning becomes the bottleneck; then verification; then taste.

> One-liner to remember: *stop tuning the prompt at 3 a.m. — write the loop.*

## 3. 🔀 Cyclomatic Complexity → [full note](../cyclomatic-complexity.md)

**What it is:** the number of linearly independent paths through code — a proxy for how hard it is to understand and test.

What actually stuck:

- Practical calc = **count decision points + 1** (`if`, loops, `case`, `catch`, `&&`, `||`, `?:`). An `else` adds nothing — it's not a new decision.
- The formal version is McCabe's `M = E − N + 2P` on the control-flow graph.
- The big insight: complexity ≈ the **minimum number of test cases** for full branch coverage. So it's a *testing budget* — complexity 40 means ~40 paths that almost never all get tested.
- It's one signal, not a verdict — it misses nesting depth (see **cognitive complexity**), data complexity, and coupling.

> One-liner to remember: *count the branches, add one — that's roughly how many tests you owe.*

## 4. 💩 CRAP Score → [full note](../crap-score.md)

**What it is:** Change Risk Anti-Patterns — combines complexity **and** test coverage into one change-risk number. `CRAP = comp² × (1 − cov)³ + comp`.

What actually stuck:

- Complex code isn't automatically dangerous — complex code **without tests** is. CRAP puts both on one axis.
- The `+ comp` term is a **floor**: at 100% coverage, `CRAP = comp`. So above complexity ~30, *no amount of testing* can rescue it — the metric is ordering you to refactor.
- Two levers, and CRAP tells you which to pull: **test simple code, refactor complex code.**
- I had to *compute the coverage thresholds*, not guess them — e.g. a complexity-20 method needs ~71% coverage to stay under the 30 ceiling. Lesson: verify the math, don't eyeball it.

> One-liner to remember: *test the simple stuff, refactor the scary stuff — CRAP says which is which.*

## 🔗 Connections I noticed

- **Verification is the common thread.** Loop engineering insists on a *separate verifier*; cyclomatic complexity quantifies *how much* verification a method demands; CRAP scores *whether that verification actually exists*. They're three views of the same discipline: don't trust code (or an agent) that grades itself.
- **State on disk shows up twice** — the "write to disk, not to context" loop rule mirrors how databases keep durable state that survives a crash and can resume.
- **Everything is a trade-off with an explicit floor** — indexes (reads vs. writes), CRAP (complexity floor even at full coverage). Good metrics make the trade-off visible instead of hiding it.
