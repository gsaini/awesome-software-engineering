## ⚖️ Load Balancing & Rate Limiting → [full note](../load-balancing-rate-limiting.md)

**The core framing:** both control flow under load, from opposite directions. A load balancer decides *where* a request goes (distribution); a rate limiter decides *whether* it goes at all (protection). Together they're how a system survives a spike or an abuser.

What actually stuck:

- **L4 vs. L7 is the key LB distinction.** L4 = fast, protocol-agnostic connection forwarding (IP/port). L7 = HTTP-aware — routes on path/host/headers, terminates TLS, rewrites. Most app traffic wants **L7**; use L4 for raw speed or non-HTTP.
- **Algorithm defaults:** **least connections** for general web traffic; **consistent hashing** when the backend is stateful/cache-bearing — only `~1/N` of keys remap when a server joins/leaves, instead of nearly all. **Power of two choices** (pick 2 random, send to the less loaded) cheaply avoids hot spots.
- **Stateless servers beat sticky sessions.** Externalize session state (Redis / signed token) so any server handles any request. Sticky sessions are a crutch — uneven load + state lost when that box dies. This is literally the concurrency "no shared mutable state" lesson at fleet scale.
- **Rate-limiting algorithms, by shape:** fixed window (simple, but boundary-burst bug: 2× at the edge) → sliding window log (exact, memory-heavy) → sliding window counter (the production compromise) → **token bucket** (allows controlled bursts — most APIs) → **leaky bucket** (smooths to a constant rate — protect a fragile downstream).
- **Distributed rate limiting is the hard part:** per-instance limits silently multiply by N. Options: centralized Redis counter (accurate, adds a hop + SPOF, needs **atomic Lua** to avoid a check-then-set race), local+sync (fast, approximate), or sticky routing. Same accuracy-vs-latency trade-off as everywhere.
- **Return `429` + `Retry-After` + `RateLimit-*` headers** so good clients back off instead of hammering.
- **Retries + rate limits interact dangerously** → retry storms. Always backoff + **jitter** + a retry cap + respect `Retry-After`.

> One-liner to remember: *L7 + least-connections (consistent hashing if stateful), stateless servers, token bucket for bursts — and never retry naively into an overloaded service.*

## 🔗 Connections I noticed

- **Jitter is now a load-bearing idea across three notes.** Cache stampede/avalanche → jitter TTLs; retry storms → jitter backoff. Randomization de-synchronizes clients so they don't all hit at once. Same fix, three problems.
- **Consistent hashing links caching, load balancing, and the Dynamo paper.** Sharded cache placement, stateful LB routing, and distributed-DB partitioning are the *same* mechanism — minimize remaps under membership change.
- **Stateless fleet = immutability at scale.** "No shared mutable state" (concurrency) → "stateless instances" (load balancing). Removing shared state removes a class of problems whether the unit is a thread or a server.
- **The distributed rate-limiter's Lua-atomicity need is a race condition** — the exact check-then-set hazard from the concurrency note, just moved to Redis. Fifth time the read-modify-write hazard has shown up.
- **Backpressure/load-shedding = fail gracefully**, the resilience instinct from caching (fail open), security (fail closed), and loop engineering (let it restart). Decide your failure mode deliberately.
