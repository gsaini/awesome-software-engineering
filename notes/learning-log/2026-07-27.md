## 🔑 Service-to-Service Authentication → [full note](../service-to-service-auth.md)

**The core reframe:** user auth is for a human authenticating occasionally and interactively. S2S auth is for a machine calling thousands of times a second, non-interactively, with credentials living in memory/config. So the whole game is **short-lived, auto-rotated, cryptographically-verifiable identity with no human in the loop** — and "inside the network" proves nothing.

What actually stuck:

- **The defining hard part is "secret zero"** — to get a credential you usually need a credential. Where does the *first* one come from, and how do you rotate thousands without downtime? Most of the sophistication in this space exists to answer that.
- **The trajectory is away from shared static secrets** → HMAC-signed requests → OAuth2 client-credentials JWTs → **mTLS** → **platform workload identity**. Each step reduces what a human touches and shortens credential life.
- **mTLS = both sides present certs.** Identity is the *key pair*, not a bearer string, so it can't be replayed without the private key — and the channel is encrypted (zero trust even internally). The catch is operational (issuing/rotating certs), which is exactly what a **service mesh** (Istio/Linkerd) automates — rotating certs every few hours with zero app code.
- **OAuth2 client-credentials grant** is the app-layer M2M standard: service gets a short-lived JWT from an auth server, presents it as a bearer token; service B validates **signature + iss + aud + exp + scope locally**, with a **pinned algorithm** (reject `alg:none` — the JWT trap from my security note). Prefer **`private_key_jwt`** over `client_secret` so no shared secret is in transit.
- **Workload identity (SPIFFE/SPIRE, cloud IAM) dissolves secret zero instead of managing it.** The platform *attests* what the workload is and where it runs, then hands it a minutes-lived SVID/credential via the metadata service. **No secret to store, leak, or rotate.** This is the endgame.
- **Bearer vs. sender-constrained tokens** decides what happens when a token leaks. A bearer token is replayable if stolen; a **sender-constrained** one (mTLS-bound RFC 8705, or DPoP RFC 9449) is bound to the client's key, so a stolen token is useless. Token-layer "assume breach."
- **AuthN ≠ AuthZ, still.** After proving *who* is calling, authorize *what* it may do — least privilege per service (caps blast radius), centralized policy (OPA), enforced on every call.

> One-liner to remember: *prefer platform workload identity and mTLS, make credentials minutes-lived and auto-rotated, validate every JWT fully (pin the alg), and least-privilege each service to cap the blast radius.*

## 🔗 Connections I noticed

- **This is my security note's principles made concrete for machines.** Zero trust → mTLS + "network isn't identity"; least privilege → per-workload identity capping blast radius; fail-closed → no valid cert/token means no connection; the JWT `alg:none` trap → pin the algorithm. The abstract principles finally have mechanisms.
- **"Secret zero" is a bootstrapping problem, like consensus bootstrapping a leader.** Both need a trusted starting point to derive everything else from — SPIRE's node attestation is the trust anchor, the way a quorum is for consensus.
- **Short-lived + auto-rotated is the "keep the window small" instinct again** — short-lived tokens are to credential theft what short TTLs are to cache staleness and short locks are to contention. Minimize the window of exposure.
- **Sender-constrained tokens = idempotency-key thinking, inverted.** Idempotency makes *replay harmless*; sender-constraint makes *replay impossible*. Two answers to "what if this request happens again / is reused."
- **Content-addressing echo:** a cert/SVID is identity derived from cryptographic material, verified without a central lookup — the same "verify by the artifact itself" idea as content-addressable stores (hash) and JWT signatures.
