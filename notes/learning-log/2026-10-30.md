## 📜 Event Sourcing & CQRS → [full note](../event-sourcing-cqrs.md)

**The core reframe:** **the log is the truth, and every table is a cache of it.** Instead of overwriting `balance = 70`, store `Deposited 100` and `Withdrawn 30`, and fold them into 70. Current state becomes a derived value.

What actually stuck:

- **Two functions are the whole pattern.** `decide(state, command) → events` can refuse, and that's where business rules live. `evolve(state, event) → state` must never refuse, because the event already happened and replay has to work. Keeping those separate clarified everything else.
- **Optimistic concurrency is one unique index.** `UNIQUE (stream, version)` means two writers from version 1 can't both append version 2. The loser reloads and decides again, and nobody holds a lock during the decision. I ran it in about 60 lines of SQLite.
- **The stream is the consistency boundary.** Rules hold within one aggregate's stream. Across streams, things are eventually consistent. A stream that keeps growing usually means the aggregate is too big, so close it on a natural boundary, the way accounting closes a period.
- **CQRS comes in degrees, and it's independent of event sourcing.** Level 0 is just separate code paths on the same tables. Fowler's warning stays with me: for most systems it "adds risky complexity".
- **The superpower is rebuilding.** A new report is a new projection that starts at position 0 and catches up alongside the old one. The trap is the same mechanism: side effects in a projection fire again on every replay, so they need their own consumer of *new* events only.
- **Schema evolution is the real cost.** Events are immutable and your code must read all of them forever. Upcasting (convert on read, v1→v2→v3) keeps the store immutable but leaves a chain you maintain forever. Overeem et al. wrote a whole paper on this, and "the dark side" is a fair title.
- **Deletion needs a decision on day one.** Immutable logs collide with erasure requests. The options are crypto-shredding, keeping personal data out of events, or rewriting the stream.
- **The test for "is this event sourcing?"** If you deleted the events, could you still run the system? Taskbox could, because its `tasks` table is the truth and `events` is an outbox. That's why it could add events in one transaction without changing how anything reads state.

> One-liner to remember: *decide can fail, evolve can't; streams are the consistency boundary; projections are disposable; and you own every event schema forever, so use it only where the history is the business.*

## 🔗 Connections I noticed

- **Durable execution is event sourcing for workflows.** Temporal's event history plus replay is exactly `evolve` over a stream, and "workflow code must be deterministic" is the same rule as "`evolve` must be pure and total". My 2026-08-04 note had this pattern without the name.
- **Stream–table duality, again.** A projection is a stream folded into a table, which is the same insight as Kafka Streams in my 2026-09-12 note. And rebuilding a projection beside the old one and switching is the blue-green move from progressive delivery.
- **Idempotency keeps coming back.** A projection into another system can't commit its checkpoint atomically, so its writes must be idempotent. Same rule as queues, durable execution, and the Taskbox webhook receivers de-duplicating on `id`.
- **Agent checkpoints are a cousin.** The graph runtime in `my-agentic-moments` stores each step's update to immutable state and can resume from any point. Agent traces are event logs, so "why did it do that?" has an answer for the same reason a ledger does.
- **The cursor in Taskbox is a projection checkpoint.** Each webhook endpoint's `cursor` is a consumer position over a log. I built the consumer half of this pattern before I had the vocabulary for it.
