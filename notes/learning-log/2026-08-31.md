## 🧩 Database Sharding & Partitioning → [full note](../database-sharding-partitioning.md)

**The core reframe:** partitioning and replication are **orthogonal and combined** — replication makes *copies* (availability/read scale), partitioning *splits* (write/storage scale). You shard when replication can't help because the data or write volume exceeds a single node. And each shard is itself replicated.

What actually stuck:

- **Don't shard prematurely.** Exhaust scale-up → read replicas → caching *first*. Sharding is one of the hardest changes to reverse; do it at a *measured* single-node ceiling, not because it sounds scalable.
- **Four strategies:** **range** (great range scans, but sequential-key hotspots), **hash** (even spread, kills range queries), **consistent hashing** (only ~1/N keys remap on rebalance — the *same* mechanism as my caching & load-balancing notes, third context), **directory/lookup** (max flexibility incl. geo/tenant homing, but an extra hop/SPOF).
- **The shard key is THE decision** — it dictates both distribution *and* which queries are cheap, and it's brutal to change later. Pick it so (a) load spreads evenly *and* (b) your hottest queries hit **one shard**. The test: "does my top query fan out to every shard?" If yes, wrong key.
- **Hash fixes *sequential* hotspots but not a *hot key*.** A celebrity/mega-tenant is one key → one shard; needs **salting/key-splitting** or a dedicated shard. Different problem, different fix.
- **Rebalancing:** never `hash % N` (remaps everything). Use **many fixed partitions** (reassign whole ones) or **dynamic split/merge** (like B-tree nodes) or consistent hashing.
- **Everything is easy within a shard and hard across shards** — cross-shard queries become scatter-gather (as slow as the slowest shard); cross-shard transactions need 2PC/saga; secondary indexes are local (scatter reads) or global (scatter writes). The whole craft is **choosing a shard key so important ops stay within one shard.**

> One-liner to remember: *shard only when you must; pick the shard key so hot queries and transactions stay on one shard; hash sequential keys, split hot keys, and never rebalance with `hash % N`.*

## 🔗 Connections I noticed

- **Consistent hashing, now a FOURTH context** — sharded caches → LB routing → event partitioning → data sharding. It might be the single most reused mechanism in my whole library. "Minimize remaps on membership change" keeps mattering.
- **"Keep it in one shard" = "keep it in one transaction" = "keep the window small."** The recurring locality/blast-radius instinct: co-locate related data so you avoid distributed transactions, just like short transactions avoid contention and short TTLs bound staleness.
- **Kafka partitions ARE sharding** — partition-by-key in my message-queue note is this exact idea for a log; cross-shard queries = cross-partition ordering. Same problem, two subsystems.
- **Each shard is a consensus group** — Spanner/Cockroach run Raft/Paxos *per shard* and do cross-shard ACID via consensus + 2PC. My consensus, consistency, sharding, and multi-region notes are all describing one machine from different angles now.
