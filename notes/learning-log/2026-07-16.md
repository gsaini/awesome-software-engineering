## 🧵 Concurrency & Parallelism → [full note](../concurrency-parallelism.md)

**The core distinction:** concurrency is about **structure** (dealing with many tasks, interleaved); parallelism is about **execution** (doing many literally at once). You can have concurrency on one core; you need concurrency to *get* parallelism, but they're not the same thing. (Rob Pike: *"concurrency is about structure, parallelism is about execution."*)

What actually stuck:

- **Almost every concurrency bug is one root cause: shared mutable state touched without coordination.** The two-thread counter losing an increment is `read-modify-write` gone wrong — the *exact same lost-update bug* from my transactions note, one layer down. Databases fix it with isolation; in-process code fixes it with locks/atomics.
- **The safest shared state is none.** Immutability, confinement, and message passing kill whole bug classes by construction. Every "safe" model (actors, CSP/Go channels) converges on the same idea: *replace shared memory with message passing.*
- **Race condition vs. data race are different:** a data race is the strict "two unsynchronized accesses, one a write" (undefined behavior in C++/Go/Rust); a race condition is the broader "correctness depends on timing." Every data race is a race condition, not vice versa.
- **Deadlock needs all four Coffman conditions** — break any one. The practical fix is #4: **acquire locks in a consistent global order** everywhere. Prevention (lock ordering) vs. avoidance (Banker's) vs. detection (what DBs do — wait-for graph + abort a victim).
- **CPU-bound vs. I/O-bound decides everything.** Async for I/O-bound (overlap the waiting); parallelism for CPU-bound. Throwing `async` at CPU work buys *nothing* — it can't overlap computation.
- **Amdahl's Law is humbling:** if 5% is inherently serial, you can never beat 20× no matter the core count. The serial part dominates — which is *why* short critical sections matter.
- **You can't reason about multicore visibility with single-threaded intuition.** CPUs/compilers reorder; caches diverge. You need a memory model's happens-before (via atomics/locks), and CAS is the workhorse of lock-free code.

> One-liner to remember: *prefer no shared mutable state; match the tool to the workload (async for I/O, parallelism for CPU); and `counter += 1` is not atomic.*

## 🔗 Connections I noticed

- **Transactions were concurrency all along.** Lost update, deadlock detection, locking (2PL) vs. MVCC — my "databases" note was really about the concurrency primitives in this note, scaled up to durable multi-node state. Mutex ≈ pessimistic 2PL; CAS/optimistic ≈ MVCC/SSI-with-retry.
- **"Let the loop restart" = "let it crash."** Erlang's actor supervision (let a process crash, a supervisor restarts it) is the same fault-tolerance instinct as loop engineering's restart-on-failure and the DB's abort-and-retry. Three notes, one idea: **cheap restart beats fragile correctness.**
- **"Hold locks briefly" = "keep transactions short" = "short TTLs."** Minimizing the window of exclusive/inconsistent access is a recurring move across concurrency, transactions, and caching.
- **Message passing is the immutability instinct again** — and it echoes zero-trust from the security note: don't share a mutable thing and hope; hand over a copy/message with a clear boundary.
