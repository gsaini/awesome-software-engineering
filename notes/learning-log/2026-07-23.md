## 📨 Message Queues & Event-Driven → [full note](../message-queues-event-driven.md)

**The core reframe:** a synchronous call couples two services in **time** (both up, right now) and **space** (caller must know the callee). A broker breaks both. The price is eventual consistency plus a new class of failure modes — duplicates, reordering, and messages that never land.

What actually stuck:

- **Queue vs. log is the big architectural fork.** A queue *consumes and removes*; a log is **append-only and immutable**, so reading is **non-destructive**. That's the whole superpower: many independent consumers at their own offsets, new services replaying from the beginning, and reprocessing after a bug fix. Kafka's model, and why it underpins CDC and event sourcing.
- **At-least-once is the practical default; exactly-once is mostly a marketing claim.** The consumer processes, then crashes before acking → the broker redelivers. You can't atomically "do the work" and "record that I did it" across two systems. **The real answer is at-least-once + idempotent consumers.** Kafka transactions give *effectively-once* inside their own boundary — but **you cannot un-send an email**.
- **Global ordering doesn't scale** (it means one consumer). Brokers give **ordering within a partition**, so you partition by the key whose order matters (usually entity ID). Too coarse a key → hot partitions; wrong key → events that must be ordered race in different partitions. Parallelism is capped by partition count.
- **A single bad message must never halt the pipeline:** retry with backoff + **jitter**, cap attempts, then **DLQ** — and *alert on DLQ depth*, because an unmonitored DLQ is a silent data-loss bucket.
- **Events vs. commands:** a command is "do this" (imperative, one handler); an **event is a past-tense fact** ("OrderPlaced"), broadcast, publisher indifferent to who reacts. Events invert the dependency — **adding a consumer requires no producer change.** That's the actual decoupling payoff.
- **The dual-write problem is the classic bug here:** `db.save()` succeeds, `broker.publish()` crashes → the order exists but nobody was told, and systems diverge permanently. Fixes: **transactional outbox** (write the row + an outbox row in one DB transaction, relay publishes) or **CDC** (tail the DB replication log — the write *is* the event source, so they can't diverge).
- **Queue depth / consumer lag is the SLI for an async pipeline** — the async equivalent of latency. An unbounded queue is *a latency problem disguised as a capacity solution*.

> One-liner to remember: *assume at-least-once and make consumers idempotent; partition by the key whose order matters; and never "save then publish" — use an outbox or CDC.*

## 🔗 Connections I noticed

- **CDC finally has a name and a justification.** My caching note said "event-driven invalidation via CDC" as a bullet; today I learned *why it's trustworthy* — it tails the DB's own replication log, so the write and the event can't diverge. It's the **dual-write fix**, not just an invalidation option.
- **Idempotency: sixth appearance, and now I see it's the load-bearing idea of reliability.** DB retry-on-serialization-failure → loop restart → concurrency let-it-crash → API `Idempotency-Key` → distributed rate limiting → message consumers. Every reliable system assumes operations **will** repeat and makes that safe. If I had to keep one principle from this whole month, it might be this one.
- **Jitter: third appearance** — cache stampede/avalanche, retry storms, and now consumer retries. Randomize so clients don't synchronize.
- **DLQ = flaky-test quarantine.** Both isolate the poison item so it stops blocking the pipeline, then alert so a human fixes it. Same operational instinct, two very different domains.
- **The leaky bucket returned** — queue buffering *is* rate limiting's smoothing pattern, seen from the consumer side. Backpressure and load shedding transfer directly.
- **Partitioning = consistent hashing, again.** Sharded caches, stateful load balancing, and now event partitioning — the same key-routing mechanism, third context.
