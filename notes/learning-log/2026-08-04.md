## ⏳ Durable Execution → [full note](../durable-execution.md)

**The core magic:** write long-running, multi-step logic as ordinary code, and a runtime guarantees it **runs to completion even if the process crashes**. State lives in a persisted **event history**, not in memory — so a killed workflow resumes on another worker as if nothing happened. You write the happy path; the runtime owns crashes, retries, and timeouts.

What actually stuck:

- **It's the Replicated State Machine from my consensus note, wearing a new hat.** Every step's result is appended to an **event history** (an append-only log); on crash, another worker **replays** the log to reconstruct exact state, then continues. "Apply the same ordered log → arrive at the same state" is literally how Raft replicas stay consistent — here applied to *my business logic*.
- **Workflows decide, activities do.** The **workflow** is deterministic orchestration (replayed); **activities** are the side-effecting I/O (retried, **at-least-once**). All the messy non-deterministic stuff is quarantined into activities.
- **Activities must be idempotent** — the runtime *will* retry them. My most-repeated lesson (idempotency, ~8th sighting) is now a *hard requirement of the model*, not a nice-to-have.
- **You get for free** what I'd otherwise hand-roll: automatic retries with backoff + **jitter**, **durable timers** (`sleep("30 days")` actually works — no cron/poller, crash-proof), timeouts, state persistence, signals/queries, child workflows.
- **Sagas become a `try/except`.** Compensation logic (undo on failure) is just an exception block because the workflow is durable — no separate saga coordinator. Makes **orchestration** (central brain) cheap enough to prefer over **choreography** (event-reacting) when you need a debuggable process.
- **The determinism constraint is the catch:** workflow code can't call `now()`/`random()`/do direct I/O (it's replayed) — get non-determinism through the runtime (durable timer, side-effect API, activities). Change workflow code mid-flight and you must **version/patch** it or replay diverges.

> One-liner to remember: *durable execution = write the happy path as code, the runtime replays an event log to survive crashes; workflows are deterministic, activities are idempotent and do the I/O.*

## 🔗 Connections I noticed

- **Event history + replay = replicated state machine = my consensus note.** Same log-then-replay mechanism, same determinism requirement — Raft for one process instead of five nodes. This is the third home for "the log is the universal abstraction" (DB WAL → Kafka → Raft → **now durable execution**).
- **The determinism rule is now a THREE-note through-line:** RSM commands (consensus), workflow code (here), and reproducible tests (testing) all forbid `now()`/`random()`/direct I/O. *If you need to replay it, it can't depend on non-deterministic inputs.*
- **It ergonomically solves the dual-write & saga problem** from my message-queue note — the thing I'd flagged as fiddly (reliably do X then Y across services) becomes plain `try/except` code.
- **Idempotency reaches ~8 sightings and is now load-bearing at the framework level** — at-least-once activities *require* it. If one principle defines "reliability" in my library, it's this.
- **Backoff + jitter and workflow versioning** are lifted straight from my caching/rate-limiting and schema-evolution notes. A "new" framework is, again, old fundamentals recomposed.
