## 🧮 Data Structures & Algorithms → [full note](../data-structures-algorithms.md)

**The core idea:** there's no universally best data structure — only the best *for your access pattern*. Choosing a structure **is** choosing which operations you've decided to make fast and which you've accepted will be slow.

What actually stuck:

- **Big-O is about growth rate, not absolute speed** — constants and lower-order terms drop because at scale the rate dominates. But three caveats bite in practice: constants *can* matter at real sizes, you must analyze **space as well as time**, and **amortized ≠ worst-case** (dynamic-array append is O(1) amortized, O(n) on resize).
- **The two default tools are the dynamic array and the hash map.** Everything else earns its place by offering an operation those two can't do cheaply: **ordering** (BST), **priority** (heap), or **cheap ends** (stack/queue).
- **Arrays beat linked lists more than theory says** — contiguous memory means the CPU cache prefetches; a linked list chases pointers across the heap. O(1) insertion rarely beats cache locality.
- **BST vs. heap in one line:** a BST keeps *everything* ordered (ranges, predecessors); a heap only tracks the *extreme* (fast min/max, nothing else). And an unbalanced BST degrades to a linked list — which is why real systems use red-black / B-trees.
- **Hashing is the most leveraged idea in the whole subject.** O(1) average, O(n) worst (collisions → real DoS vector), no ordering, amortized resize. And it's *everywhere upstream*: DB hash indexes, consistent hashing, content-addressable stores (pnpm/Git), Bloom filters, dedup sets.
- **Graph algorithms are built out of the earlier structures:** BFS is a queue, DFS is a stack, Dijkstra is a heap. The structures are the alphabet; the algorithms are the words.
- **Paradigms > memorized solutions:** two-pointers/sliding-window, binary search (on any monotonic predicate), divide-and-conquer, DP (overlapping subproblems), greedy (only when local optimum ⇒ global — prove it), backtracking.

> One-liner to remember: *pick the structure from the access pattern, reach for a hash map to break O(n²), and prefer arrays for iteration — cache locality beats theoretical O(1) insert.*

## 🔗 Connections I noticed — the foundation under the month

Studying this *last* was accidentally perfect: I recognized these structures because I'd already seen them at scale.

- **B-trees are my indexing note; consistent hashing is my caching + load-balancing notes; the replicated log is a queue.** The "big" systems topics were data structures wearing bigger hats. Learning them top-down, then seeing the fundamentals, made both stick harder.
- **The space-vs-time trade-off IS the read-vs-write trade-off** — the meta-pattern I kept tallying all month (indexes, caches, MVCC, cardinality) is, at bottom, "spend memory to save time." This note is its most primitive form.
- **Amortization connects DSA to storage:** dynamic-array resize, hash-map rehash, and B-tree/LSM compaction are the same "occasional expensive op spread over many cheap ones" idea.
- **"Measure, find the bottleneck, fix the real one"** — the problem-solving loop here is the same discipline as observability debugging and the CRAP-score "test the scary parts" instinct. Don't optimize by guess.
- **Content-addressable storage = hashing**, full stop. pnpm's store and Git's object model are just "hash the content, use it as the key." I'd noted that twice without naming the underlying structure.
