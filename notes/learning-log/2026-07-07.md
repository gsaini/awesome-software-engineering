## 🧪 Building an Agent Evaluator → [full note](../building-agent-evaluators.md)

**The core principle:** never let a loop grade its own work. A generator that scores its own output turns sycophantic and converges on slop. Quality comes from an **independent evaluator** — same reason we separate authors from reviewers, and code from its tests.

What actually stuck:

- **Evaluate at three levels:** end-to-end (did the goal get met?), trajectory (was the path sound/efficient?), and component (which tool/retriever broke?). End-to-end tells you *that* it failed; the other two tell you *why* — which is what you actually fix.
- **Outcome ≠ trajectory.** An agent can call every tool correctly and still fail the task; and it can reach the right answer via a terrible, expensive path. Grade both.
- **Pick the right judge:** deterministic checks for objective things (schema, JSON parse, tool-call format, code-runs-and-passes-tests) — run on 100% of outputs at ~zero cost — and **LLM-as-judge only for the subjective stuff** deterministic checks can't express.
- **LLM judges are biased** — position bias, verbosity bias, self-preference. Mitigations: swap answer order and average, anchor with an explicit rubric, require justification *before* the score, and use a *different* model family as the judge.
- **Calibrate the judge against human labels** — measure agreement. An uncalibrated judge is just a second opinion you can't trust.
- **Evals are versioned datasets**, not vibe checks. Guideline: ≥500 cases before trusting aggregate metrics; grow the set from real failure traces; track it in git like a test suite.

> One-liner to remember: *deterministic for objective, LLM-as-judge for subjective, human to calibrate the judge — and never let the agent mark its own homework.*

## 🔒 Database Transactions & Isolation Levels → [full note](../database-transactions-isolation.md)

**The core idea:** a transaction is all-or-nothing (ACID), and isolation is the one property with a *dial* — how much concurrent transactions can see each other's in-flight work, trading correctness for concurrency.

What actually stuck:

- **You pick an isolation level by choosing which anomalies you can tolerate:** dirty read → non-repeatable read → phantom → (lost update, write skew). Weaker level = more anomalies allowed = more concurrency.
- The four ANSI levels — **Read Uncommitted → Read Committed → Repeatable Read → Serializable** — each forbid one more anomaly. Serializable = "as if the transactions ran one at a time."
- **MVCC is the modern default:** keep multiple row versions so *readers never block writers and writers never block readers.* That's how Postgres/Oracle/InnoDB give strong read consistency without read locks.
- **Snapshot isolation still allows write skew** — the sneaky one. Two txns read a snapshot, decide independently, write different rows, and together break an invariant (the on-call-doctors example). Only Serializable (Postgres SSI) catches it — or an explicit `SELECT ... FOR UPDATE`.
- **Defaults and naming lie:** Postgres defaults to Read Committed; MySQL to Repeatable Read; Oracle's "Serializable" is really snapshot isolation. Two DBs at "the same" level can behave differently.

> One-liner to remember: *pick the weakest isolation level that keeps the data correct — and don't assume snapshot isolation is serializable.*

## 🔗 Connections I noticed

- **This is the verifier from loop engineering, made concrete.** Yesterday's "separate the roles / negotiate the contract" is *why*; today's rubrics, gates, and eval sets are *how*. The contract literally becomes the rubric.
- **The verification thread keeps compounding.** Loops need a separate verifier → the evaluator *is* that verifier → and its "coverage theater" trap (an eval that runs but asserts nothing) is the same failure I saw in the [CRAP score](../crap-score.md) note: coverage ≠ assertions.
- **Layered like defense in depth** — cheap deterministic gates first, expensive LLM judgment last. Same shape as good input validation or a test pyramid.
- **"Retry on serialization failure" is a loop.** Postgres SSI aborts conflicting transactions and expects the app to retry — the same *let-the-loop-restart* pattern from loop engineering, just at the database layer.
- **Everything is the same read-vs-write trade-off.** Indexes trade write cost for read speed; isolation trades concurrency for correctness; MVCC trades storage (old versions) for lock-free reads. Good systems make the trade-off explicit.
