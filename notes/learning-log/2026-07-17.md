## 🔌 API Design (REST / gRPC / GraphQL) → [full note](../api-design.md)

**The core reframe:** an API is a **contract**, not code. Internal code optimizes for *change*; a public API optimizes for *stability* — once someone integrates, your mistakes are permanent until a major version. Design the interface as if you can't take it back, because mostly you can't.

What actually stuck:

- **The three styles optimize different axes**, there's no "best": REST = resources + HTTP verbs (public, cacheable, ubiquitous); gRPC = binary RPC over HTTP/2 (fast, strict contract, internal service-to-service); GraphQL = client picks the fields (kills over/under-fetching for many varied clients).
- **REST done right is mostly discipline:** nouns for resources, HTTP verbs for actions (`POST /createUser` is the #1 smell), and **honest status codes**. `200 OK` with an error body lies to every client, proxy, and cache.
- **Safe vs. idempotent is the useful lens on HTTP methods:** GET safe+idempotent; PUT/DELETE idempotent-not-safe; POST neither. This is *exactly* the idempotency thread — retries are only safe if the operation is idempotent (naturally, or via an `Idempotency-Key`).
- **REST's structural superpower is HTTP caching** — GETs cache in browsers/CDNs/proxies via `ETag`/`Cache-Control`. GraphQL mostly *loses* this (everything is `POST /graphql`), which is a real cost, not a footnote.
- **GraphQL's hidden bills:** the N+1 problem (fix: DataLoader batching), query cost control (depth/complexity limits, not request counts), and harder observability (key metrics on operation name, not URL).
- **Versioning golden rule: additive is cheap, removal is expensive.** REST → `/v1/` in the path; protobuf → *never reuse a field tag*, only add + reserve; GraphQL → versionless, `@deprecated` instead of v2. Design fields optional and forward-tolerant so you rarely need a v2 (Postel's law).
- **Pagination: cursor/keyset over offset/limit** at scale — offset skips/duplicates rows when data shifts mid-scroll and gets slow on deep pages.

> One-liner to remember: *an API is a contract — nouns + honest status codes, additive changes only, idempotent writes, and always paginate.*

## 🔗 Connections I noticed

- **This note is a hub — four earlier notes plug straight in.** Caching (REST's `ETag` advantage), security (authz on every request = OWASP #1), observability (per-endpoint traces + the GraphQL POST gotcha), and idempotency/transactions (safe retries). API design is where a lot of my separate threads meet.
- **Idempotency keeps recurring, now the fourth time:** DB "retry on serialization failure" → loop "let it restart" → concurrency "let it crash" → API "`Idempotency-Key` so a retry doesn't double-charge." Reliable systems assume operations *will* be repeated and make that safe.
- **"Additive change is cheap" = protobuf field tags = DB schema evolution = forward-tolerant design.** The same evolvability instinct across API versioning and DDIA Ch. 4's encoding chapter.
