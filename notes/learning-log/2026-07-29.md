## 🔄 Serialization & Schema Evolution → [full note](../serialization-schema-evolution.md)

**The core reframe:** in one program, changing a struct is free — you recompile everything at once. In a distributed system **you can never upgrade everyone simultaneously**, so old and new code, old and new data, coexist for hours or years. The real question isn't "what format?" but "**can new readers understand old data, and old readers understand new data?**"

What actually stuck:

- **Forward vs. backward compatibility are independent, and you usually need both.** Backward = new code reads old data; forward = old code reads new data. During any rollout, producers and consumers upgrade in arbitrary order, so *both* directions of data flow at once. That's why "full compatibility" matters — it's the precise version of the independent-deploy problem I'd hit twice before.
- **The golden rule across every format: add and deprecate, never mutate or reuse.** Adding an **optional field with a default** is the workhorse — old readers ignore it (forward), new readers default it when absent (backward). Renaming, retyping, or optional→required are breaking.
- **Text vs. binary is the humans-vs-machines trade-off again.** JSON = readable, ubiquitous, verbose (repeats field names every record); Protobuf/Avro = compact/fast because they replace names with numeric **field tags** defined once in the schema — which is *also* why they evolve well.
- **Protobuf identity is the field NUMBER, not the name** — so you can rename freely but must **never renumber or reuse a tag** (silent data corruption). `reserved` retired tags. **Avro matches by name + defaults**, comparing writer and reader schemas — the default is what makes both directions work.
- **Never use language-native serialization across a boundary** (pickle/Java Serializable) — lock-in *and* deserializing untrusted data = RCE (the insecure-deserialization vuln from my security note).
- **A schema registry is the enforced contract** — producers register, messages carry a tiny schema ID, consumers fetch by ID, and the registry **rejects** incompatible schema changes before they ship. Compatibility becomes CI-gated, not hoped for.

> One-liner to remember: *add optional fields with defaults, never reuse a field tag, keep JSON at the public edge and binary+registry internally — and remember old and new data always coexist.*

## 🔗 Connections I noticed

- **This note names what three earlier notes only gestured at.** API versioning said "additive is cheap, removal is expensive"; message queues said "version your event schemas"; both were really *forward/backward compatibility* — I just didn't have the vocabulary. Today gave it teeth.
- **A schema registry is contract testing for data.** It's the same enforced, versioned producer↔consumer contract as an OpenAPI/`.proto` spec or a Pact test — the [testing note's](../testing-strategy.md) idea applied to bytes on a queue.
- **"Field tags not names" is the same compression instinct as everything binary** — replace a repeated string with a small stable identifier defined once. It rhymes with hashing/content-addressing (replace content with a short key) and with normalized DB keys.
- **Postel's Law is the through-line** — "be liberal in what you accept, conservative in what you send" showed up in API design and now here as the *engineering discipline* behind forward compatibility (tolerate unknown fields).
- **Edge-vs-internal split, third time:** JSON at the public edge + binary internally mirrors REST-edge/gRPC-internal (API note) and public-auth/mTLS-internal (S2S note). Same architecture, different layer.
