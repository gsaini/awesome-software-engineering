## ⚡ Caching Strategies & Invalidation → [full note](../caching-strategies.md)

**The core idea:** a cache is a fast, temporary *copy of the truth*. It buys latency and load relief in exchange for the risk of staleness — so every caching decision is really a decision about *how stale is acceptable*.

What actually stuck:

- **Caches live at every layer** — browser → CDN/edge → reverse proxy → app in-process → distributed (Redis) → DB buffer pool. Serve as high up (close to the user) as possible.
- **Read + write patterns mix and match:** cache-aside (the default — app checks cache, loads on miss) for reads; write-through / write-behind / write-around for writes. Most systems = **cache-aside + delete-on-write**.
- **Eviction policy = what to drop when full:** LRU is the sensible default; LFU for stable popularity; TTL as an upper bound on staleness on top.
- **Invalidation, from simple to fresh:** TTL → delete-on-write → write-through update → versioned keys → event-driven (CDC/pub-sub). Start with TTLs; escalate only when needed.
- **Three named failure modes:** *stampede* (hot key expires, herd hits DB — fix with single-flight/locking + jitter), *penetration* (missing keys always miss — fix with negative caching / Bloom filter), *avalanche* (mass simultaneous expiry — fix with TTL jitter).
- **The cache-aside race:** prefer **delete over update**, delete *after* commit, and always keep a TTL as a self-healing backstop. App caching is usually eventually consistent — design for "recently stale is OK."

> One-liner to remember: *a TTL is a promise about how stale a read can be — pick it deliberately, and always delete-on-write rather than update.*

## 🔗 Connections I noticed

- **The read-vs-write trade-off shows up a fourth time.** Indexes trade write cost for read speed; isolation trades concurrency for correctness; MVCC trades storage for lock-free reads; **caching trades freshness for read speed.** Same shape, different knob.
- **A TTL is to staleness what an isolation level is to anomalies** — an explicit dial on how much inconsistency you'll tolerate. Both make the trade-off visible instead of hidden.
- **A cache is "derived data."** Event-driven invalidation via CDC is literally built on the [log](../papers/) idea — the same backbone under databases and streaming.
- **Fail open** mirrors the resilience mindset from loop engineering — degrade gracefully (serve from origin) instead of erroring when a non-authoritative component dies.
