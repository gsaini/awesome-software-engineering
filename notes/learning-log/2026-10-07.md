## 📚 Retrieval-Augmented Generation → [full note](../retrieval-augmented-generation.md)

**The core reframe:** **RAG is a search problem with a language model at the end.** When a RAG answer is wrong, the cause is usually that the right passage was never retrieved, not that the model wrote badly. So measure **recall@k** before touching the prompt.

What actually stuck:

- **Parametric vs. non-parametric knowledge.** Weights are frozen, public, and unattributable. Retrieval is current, private, citable, and *permissionable*. That last property is underrated: you can't make weights forget a document for one user, but you can filter a query.
- **Chunking is the most underrated knob.** No retriever can recover a fact that chunking split in half. Structure-aware splitting is the default, and every chunk needs its metadata (source, section, date, ACL).
- **Contextual Retrieval** (Anthropic, 2024): prepend a short, model-written context to each chunk before embedding and BM25 indexing. That cut failed retrievals by 35% (embeddings alone) → 49% (+ contextual BM25) → 67% (+ reranking). It fixes the "Revenue grew 3%… *whose* revenue?" problem.
- **Hybrid + RRF + rerank is the production baseline.** BM25 catches exact tokens (error codes, SKUs) that vectors blur. Vectors catch paraphrases. Fuse by **rank**, not score (`1/(60 + rank)`), then let a cross-encoder rerank ~100 candidates down to ~10. Cheap methods for recall, expensive ones for precision.
- **Lost in the middle.** Models use the start and end of a long context better than the middle. So more chunks isn't safer: weak passages dilute strong ones and push them into the dead zone.
- **Long context hasn't killed RAG, but it moved the line.** Below ~200K tokens (~500 pages), just put the whole corpus in the prompt with caching. Above that, or with per-user permissions, high volume, or fast-changing data, retrieve. **Fine-tune for form, retrieve for facts.**
- **Evaluate the two halves separately.** Retrieval: recall@k and MRR. Generation: faithfulness, citation correctness, and *abstention* on unanswerable questions. Barnett et al.'s seven failure points split cleanly: 1–3 happen before the model sees anything (corpus, retrieval, prompt assembly), and 4–7 happen in generation.
- **Retrieved text is untrusted input.** Indirect prompt injection rides in on documents. Enforce ACLs *inside* the retrieval query, never by asking the model to keep a secret.

> One-liner to remember: *chunk with context, retrieve hybrid, fuse by rank, rerank for precision, cite or abstain, and measure recall@k before you touch the prompt.*

## 🔗 Connections I noticed

- **An ANN index is just another index.** HNSW is a layered graph you descend greedily; a B-tree is a tree you descend by comparison. Same goal as my database-indexing note: avoid the full scan, and pay for it with memory and write cost. `ef_search` and `nprobe` are one more recall-vs-latency dial.
- **The vector index is derived data,** so everything from caching and CDC applies: incremental updates driven by change events, *deletes as well as upserts*, and blue-green index swaps behind an alias (the progressive-delivery pattern again). Changing the embedding model is a schema migration with no backward compatibility, so you must re-embed everything.
- **Self-RAG and Corrective RAG are critique loops.** The critic grades *passages* instead of code, and a poor grade triggers a re-query instead of a revision. It's the same graph shape as my critique-agent note: generate → grade → route.
- **Agentic search beats vectors for code.** Names, imports, and call sites are already an index that is never stale. That explains why coding agents grep instead of embed, and it ties back to the harness notes: the tool *is* the retriever.
- **Golden sets everywhere.** The RAG eval set (labeled passages + reference answers + unanswerable questions) is the hidden-test idea from my critique-graph repo and the versioned-dataset rule from the evaluator note. Same rule each time: grade with something the system never saw.
