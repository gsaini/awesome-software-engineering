## 🚦 Feature Flags & Progressive Delivery → [full note](../feature-flags-progressive-delivery.md)

**The core reframe:** **deploy ≠ release.** Deploying puts code on servers (a technical event); releasing exposes behaviour to users (a business decision). Most outages come from fusing them. Separate them and you deploy continuously, dark, and release deliberately — 1% → 10% → everyone — with a kill switch throughout.

What actually stuck:

- **Rollback becomes seconds, not minutes.** "Revert, rebuild, redeploy" becomes "flip a switch." And decoupling is what makes **trunk-based development** possible — unfinished work merges to `main` behind an off flag.
- **Sticky bucketing matters.** Percentage rollouts must hash the user (`hash(userId) % 100`) so the same person consistently sees the same variant — random-per-request flips them between old and new on every click.
- **The flag service's outage default *is* your outage behaviour.** Choose it per flag: new risky feature → fail safe to off. That's the fail-open-vs-fail-closed call from my security note, again.
- **Four kinds of flag, very different lifespans** (Hodgson): **release** (short — must die), **experiment** (test-length), **ops** (kill switches — can live long), **permission** (entitlements — long). Treating them the same is how flag debt starts.
- **Canary moves a version across traffic; a flag moves a feature across users.** They compose — canary the deploy for infra safety, flag-roll the feature for product safety. Plus blue-green (instant rollback, 2× infra, shared DB), rolling, dark launch, ring deployments.
- **Progressive delivery is only as good as its signals.** Compare canary *vs. baseline* (not an absolute), gate each stage on SLOs + a business metric, **auto-roll back**, and hold a bake time. Widening without watching is just a slow big-bang.
- **Code rolls back in seconds; data doesn't.** Old and new code share one database, so schema changes use **expand → migrate → switch → contract**, reversible until the final step.
- **Knight Capital (2012)** is the cautionary tale: a repurposed flag reactivated dead code on one un-updated server — **over $460M lost in ~45 minutes**. Never reuse a flag name; delete dead paths.

> One-liner to remember: *deploy dark, release deliberately — gate every widening on signals against a baseline, keep schema changes expand/contract, and kill release flags the moment they hit 100%.*

## 🔗 Connections I noticed

- **The error budget becomes a deployment gate.** In my observability note it *described* reliability; here it *decides* whether a rollout continues. Metrics stop being passive dashboards and become control inputs — the same shift as policy-as-code turning config into a gate.
- **Expand/contract = additive-first schema evolution = provider-before-consumer.** My serialization note, OpenSpec cross-repo rollout, and now database migrations all obey one rule: *add first, remove last, stay compatible so nothing moves in lockstep.* Fourth context.
- **Ring deployments generalise "deploy region-by-region."** The multi-region blast-radius rule is one instance of a broader pattern: widen in concentric rings, stop at the first sign of trouble.
- **OpenFeature is OpenTelemetry for flags.** Same vendor-neutral-API move, same CNCF home — decouple your code from the vendor.
- **Knight Capital is a dead-code disaster,** which makes Knip-style dead-code removal a *risk control*, not just tidiness.
