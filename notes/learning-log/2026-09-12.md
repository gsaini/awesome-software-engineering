## 🌊 Stream Processing → [full note](../stream-processing.md)

**The core reframe:** batch assumes the data is **finished** — see it all, sort it, compute an exact answer. A stream is **never finished**. Every hard problem here descends from that: you must answer over data that is incomplete, out of order, and sometimes late. Stream processing is really **deciding when you know enough to emit an answer** — and what to do when you were wrong.

What actually stuck:

- **Stateless vs. stateful is the difficulty line.** `map`/`filter` are trivially parallel and recoverable. `aggregate`/`join`/`window` must *remember* — so state has to be **partitioned, durable, and consistent with your stream position**. That's the whole operational burden.
- **Three clocks, and conflating them is the classic bug:** event time (when it happened), ingestion time, processing time. **You almost always want event time** — "orders in the 3pm hour" is about when orders happened, not when a lagging consumer caught up. Use processing time by accident and your results silently change whenever a consumer lags.
- **Watermarks are the "I've probably seen everything up to T" heuristic** that lets a window emit instead of waiting forever. Advance aggressively → low latency, more late data; conservatively → complete but slow. **It's a completeness-vs-latency dial — the same knob as a cache TTL or an isolation level.**
- **Windows:** tumbling (fixed, non-overlapping), hopping/sliding (overlapping — multiplies state *and* output), session (gap-based, most expressive and most state-hungry), global.
- **Stream–table duality is the elegant bit:** a stream is a **changelog** of a table; a table is the **snapshot** you get by collapsing that changelog (latest value per key). A compacted Kafka topic literally *is* a table. Joins follow: stream–table = enrichment (cheap), stream–stream = must be windowed, table–table = materialised view.
- **"Exactly-once" is exactly-once *within the framework's boundary*.** Kafka Streams wraps read-process-write-commit in one transaction; Flink uses checkpoints + 2PC sinks. But **any external side effect drops you back to at-least-once** — so the handler must be idempotent.
- **Parallelism is capped by partition count**, and **repartitioning (rekeying) is the expensive operation**. Design keys to avoid shuffles.
- **Kappa beat Lambda** because a retained, replayable log makes reprocessing trivial — and maintaining the same business logic twice in two systems reliably diverges.

> One-liner to remember: *a stream is never finished — so use event time with watermarks as your completeness/latency dial, co-partition on the key you join or aggregate by, and keep handlers idempotent because exactly-once stops at the boundary.*

## 🔗 Connections I noticed

- **The key-choice craft is identical to sharding.** "Co-partition on the join key or the operator can't see the data it needs" is *exactly* the shard-key discipline from 2026-08-31 — pick the key so related records land together, and avoid the shuffle. Third context for the same skill (DB sharding → Kafka partitioning → stream operator state).
- **Exactly-once's boundary caveat is word-for-word the durable-execution lesson.** *You cannot un-send an email.* **Idempotency is now at ~10 sightings** and is unambiguously the single most load-bearing principle in this library.
- **Watermark = TTL = isolation level.** Another explicit dial on "how much incorrectness will I accept for speed." That family of knobs now spans caching, transactions, consistency, and time.
- **Stream–table duality is the log theme completing itself.** DB write-ahead log → Kafka → Raft → durable execution → git commits → and now *the formal statement* that a changelog and a table are two views of one thing. This might be the deepest idea I've collected.
- **"Don't stream if batch will do"** joins don't-shard-early, don't-K8s-by-default, and loop-before-graph. The restraint pattern is fully general by now.
