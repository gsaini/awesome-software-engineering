## 📦 Containers & Orchestration → [full note](../containers-orchestration.md)

**Two reframes:** (1) a container is **not a lightweight VM** — it's **just a Linux process** with its own namespaces (what it can *see*) + cgroups (what it can *use*), sharing the host kernel. (2) Kubernetes is **not a deploy script** — it's a **desired-state reconcile loop**: declare what you want, controllers converge reality to it, forever.

What actually stuck:

- **Containers vs VMs:** VMs virtualize *hardware* (full guest OS each); containers virtualize the *OS* (share the kernel). Containers = fast/small/dense; VMs = stronger isolation. Often combined (containers inside cloud VMs).
- **A container = three Linux features:** **namespaces** (PID/net/mount/user… isolation), **cgroups** (CPU/mem limits), **overlayfs** (layered filesystem). No magic box — the "look under the hood and the magic disappears" payoff, like git internals.
- **Images are layered, content-addressed, cached.** Each Dockerfile instruction = a hashed layer, reused across builds/images. **Same content-addressing as pnpm's store & git objects — 4th home for it.** Dockerfile best practices (order for cache, multi-stage, small base, non-root, pin versions) all flow from the layer model. An image is a **supply-chain artifact** → scan/SBOM/sign (A03).
- **Why orchestration:** one host is easy; a fleet needs scheduling, scaling, self-healing, discovery, rollouts — that's Kubernetes (descended from Borg).
- **K8s = the reconcile loop.** Declare desired state → controllers continuously converge actual → desired. Self-healing is just "the loop noticing drift." **This is Terraform's declarative-idempotent model, made continuous** — re-applying a manifest is a no-op.
- **etcd is Raft** — so the control plane wants an **odd 3/5-member quorum**. My consensus note runs inside every cluster.
- **Core objects:** Pod (smallest unit) → ReplicaSet → **Deployment** (rolling updates), **Service** (stable L4 endpoint over ephemeral pods), **Ingress** (L7), ConfigMap/Secret, StatefulSet (state), Namespace. Labels/selectors = loose coupling; HPA = autoscaling. **Stateless pods behind a Service = the stateless-fleet + LB principle, native.**
- **Don't reach for K8s by default** — it's a real operational commitment; a PaaS/serverless/single container is often right. Same "simplest thing that works" as loop-vs-graph and don't-shard-early.

> One-liner to remember: *a container is a namespaced, cgroup-capped process on a layered filesystem; Kubernetes is a desired-state reconcile loop that heals drift — declare it, don't script it.*

## 🔗 Connections I noticed — the infra arc closes

- **Declarative desired-state + reconcile, a THIRD time** — Terraform (one-shot converge), K8s controllers (continuous converge), and durable-execution (replay to converge). Plus GitOps = the K8s reconcile loop sourced from git. Idempotency and "converge to desired state" is *the* operating-model of modern infra.
- **Content-addressed layers = hashing, 4th context** — pnpm store → git objects → (data sharding) → image layers. Hash the content, key by hash, dedupe.
- **etcd = Raft = my consensus note** — odd-member quorum, in production, inside K8s.
- **The infra arc is now complete and self-connecting:** replicate (multi-region) → split (sharding) → provision from code (IaC) → **run & orchestrate (containers/K8s)**. IaC provisions the cluster; the cluster runs the containers; each shard/region is a workload on it.
- **"Use the simplest thing that works"** — loop-vs-graph, don't-shard-early, don't-K8s-by-default: the same restraint, three domains.
